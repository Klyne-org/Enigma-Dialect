# Python Bindings Integration Plan

This document is a complete handoff spec for adding Python bindings to
`Enigma-Dialect` so that the sibling `Enigma-DSL` Python project can
construct MLIR IR directly (instead of emitting MSL text strings).

The goal is **not** to add new dialect ops. The goal is to expose the
ops already defined in `include/enigma/Dialect/Enigma/IR/EnigmaOps.td`
to Python, so Python code can build `enigma.kernel`,
`enigma.thread_position_in_grid`, etc. programmatically.

When complete, Python users will be able to do:

```python
from mlir import ir
from mlir.dialects import enigma

with ir.Context() as ctx, ir.Location.unknown():
    enigma.register_dialect(ctx)
    module = ir.Module.create()
    # ... construct enigma dialect ops programmatically
```

---

## Architectural Context (Who Writes What, Who Ships What)

This bindings work lives entirely in `Enigma-Dialect`. The sibling
`Enigma-DSL` project does NOT write any bindings, C++, TableGen, or
pybind11 code. It only *consumes* the bindings produced here.

This mirrors how Triton, CuTe DSL, IREE, and Torch-MLIR are structured:
the dialect is a **library**, the DSL is the **product**.

### Responsibility split

| Concern | Lives in |
|---------|----------|
| Dialect ops (`.td`) | **Enigma-Dialect** (already exists) |
| C API for dialect registration | **Enigma-Dialect** (this document) |
| pybind11 extension module | **Enigma-Dialect** (this document) |
| TableGen-generated op classes | **Enigma-Dialect** (auto-generated) |
| Passes + MSL codegen (`enigma-translate`) | **Enigma-Dialect** (already exists) |
| `@enigma.kernel` decorator, tracing, runtime | **Enigma-DSL** |
| MLIR-based emitter (`mlir_emitter.py`) | **Enigma-DSL** (consumes bindings) |
| `pyproject.toml`, wheel packaging, PyPI | **Enigma-DSL** |

### Distribution model

- **Enigma-Dialect is NOT published to PyPI.** It is a build-time
  dependency that produces a Python package directory
  (`build/python_packages/mlir_enigma/`) plus `.dylib` artifacts.
- **Enigma-DSL produces the user-facing wheel** and bundles the
  dialect's bindings + `.dylib` files + LLVM runtime libs inside it.
- End users `pip install enigma-dsl` and get everything at once. They
  never interact with the dialect directly, same way users of `lxml`
  never install `libxml2` themselves.

### How Enigma-DSL will consume these bindings

After this plan is complete, the DSL side does nothing more than:

```python
# In Enigma-DSL: enigma/compiler/mlir_emitter.py
from mlir import ir
from mlir.dialects import func, memref, arith
from mlir.dialects import enigma   # ← bindings produced by THIS repo
```

During development, the DSL picks them up by pointing `PYTHONPATH` at
`Enigma-Dialect/build/python_packages/mlir_enigma/`. For distribution,
the DSL's wheel build copies that directory into the wheel. Either way,
the bindings are written once here and reused everywhere.

### What success looks like for this repo

When the checklist at the end of this document passes, the contract
with Enigma-DSL is satisfied:

1. `from mlir.dialects import enigma` works from any Python process
   with `PYTHONPATH` set to the built package dir.
2. `enigma.register_dialect(ctx)` registers the dialect.
3. Every op in `EnigmaOps.td` has a corresponding auto-generated
   Python op builder class.
4. `module.operation.verify()` passes on programmatically-built IR.

Nothing more is required from this repo. The DSL takes it from there.

## Prerequisites

1. **LLVM built with Python bindings enabled.**
   `Enigma-Dialect` must be configured against an LLVM build produced
   with `-DMLIR_ENABLE_BINDINGS_PYTHON=ON`. Homebrew's LLVM does NOT
   ship these — you must build LLVM from source (or pull a prebuilt
   artifact that includes the bindings).

2. **`pybind11` headers available** (usually comes with the LLVM
   Python-enabled build, or `brew install pybind11`).

3. **Python 3.10+** matching the Python used to build LLVM.

## Deliverables Overview

We are adding four small layers on top of the existing dialect. None
of them introduce new ops. They only *expose* what is already there.

| Layer | Purpose | Files touched | Approx LOC |
|-------|---------|---------------|------------|
| 1 | C API for dialect registration | `include/enigma-c/`, `lib/CAPI/` | ~15 |
| 2 | pybind11 extension module | `python/EnigmaModule.cpp` | ~20 |
| 3 | TableGen wrapper + Python stubs | `python/mlir_enigma/` | ~15 |
| 4 | CMake glue to tie it all together | `CMakeLists.txt`, `python/CMakeLists.txt` | ~50 |

Total: ~100 lines of hand-written code, plus the CMake wiring.
Everything else (op builder classes, type conversions) is generated by
MLIR TableGen from the existing `EnigmaOps.td`.

## Layer 1 — C API

MLIR's Python bindings talk to C++ dialects via a C API. You write a
tiny wrapper that exposes `mlirGetDialectHandle__enigma__()`.

### New file: `include/enigma-c/Dialects.h`

```c
#ifndef ENIGMA_C_DIALECTS_H
#define ENIGMA_C_DIALECTS_H

#include "mlir-c/IR.h"

#ifdef __cplusplus
extern "C" {
#endif

MLIR_CAPI_EXPORTED MlirDialectHandle mlirGetDialectHandle__enigma__(void);

#ifdef __cplusplus
}
#endif

#endif // ENIGMA_C_DIALECTS_H
```

### New file: `lib/CAPI/Dialects.cpp`

```cpp
#include "enigma-c/Dialects.h"
#include "mlir/CAPI/Registration.h"
#include "enigma/Dialect/Enigma/IR/EnigmaDialect.h"

MLIR_DEFINE_CAPI_DIALECT_REGISTRATION(Enigma, enigma,
                                      mlir::enigma::EnigmaDialect)
```

> If your dialect's C++ namespace isn't `mlir::enigma`, adjust the
> third macro argument accordingly. The first argument is a C-safe
> token, the second matches the dialect's mnemonic from `.td`, the
> third is the C++ class.

### New file: `lib/CAPI/CMakeLists.txt`

```cmake
add_mlir_public_c_api_library(MLIREnigmaCAPI
  Dialects.cpp

  LINK_LIBS PUBLIC
  MLIRIR
  MLIREnigmaDialect  # whatever your dialect's C++ library target is named
)
```

### Update: `lib/CMakeLists.txt`

Add at the bottom:

```cmake
add_subdirectory(CAPI)
```

## Layer 2 — pybind11 Extension

This is the one small chunk of hand-written C++ that exposes
`register_dialect()` to Python.

### New file: `python/EnigmaModule.cpp`

```cpp
#include "enigma-c/Dialects.h"
#include "mlir/Bindings/Python/PybindAdaptors.h"

namespace py = pybind11;
using namespace mlir::python::adaptors;

PYBIND11_MODULE(_mlirDialectsEnigma, m) {
  m.doc() = "Enigma dialect Python bindings";

  m.def(
      "register_dialect",
      [](MlirContext context, bool load) {
        MlirDialectHandle handle = mlirGetDialectHandle__enigma__();
        mlirDialectHandleRegisterDialect(handle, context);
        if (load) {
          mlirDialectHandleLoadDialect(handle, context);
        }
      },
      py::arg("context"), py::arg("load") = true);
}
```

That's the whole file. No new types, no new ops — just dialect
registration. Everything else flows through MLIR's generic Python
op-builder machinery.

## Layer 3 — TableGen Wrapper + Python Stubs

### New file: `python/mlir_enigma/dialects/EnigmaOps.td`

This is a shim that re-exports your existing op definitions into the
Python bindings TableGen pipeline.

```tablegen
#ifndef PYTHON_BINDINGS_ENIGMA_OPS
#define PYTHON_BINDINGS_ENIGMA_OPS

include "mlir/Bindings/Python/Attributes.td"
include "enigma/Dialect/Enigma/IR/EnigmaOps.td"

#endif
```

### New file: `python/mlir_enigma/dialects/enigma.py`

Thin re-export so `from mlir.dialects import enigma` works:

```python
from ._enigma_ops_gen import *
from .._mlir_libs._mlirDialectsEnigma import *
```

The `_enigma_ops_gen` module is AUTO-GENERATED by TableGen during the
build — do not commit it, and do not hand-write it.

### New file: `python/mlir_enigma/__init__.py`

Empty file (package marker). That's it.

## Layer 4 — CMake Glue

This is the messy part. MLIR provides CMake macros that do most of
the heavy lifting, but you have to wire them up.

### Update: root `CMakeLists.txt`

Near the top, add an option:

```cmake
option(ENIGMA_ENABLE_PYTHON_BINDINGS "Build Python bindings" OFF)
```

Near the bottom, after `add_subdirectory(lib)` and `add_subdirectory(tools)`:

```cmake
if(ENIGMA_ENABLE_PYTHON_BINDINGS)
  include(MLIRDetectPythonEnv)
  mlir_configure_python_dev_packages()
  add_subdirectory(python)
endif()
```

### New file: `python/CMakeLists.txt`

```cmake
include(AddMLIRPython)

# Root of the generated Python package tree
set(ENIGMA_PYTHON_ROOT_PREFIX "${CMAKE_CURRENT_BINARY_DIR}/python_packages/mlir_enigma")

declare_mlir_python_sources(EnigmaPythonSources)

declare_mlir_python_sources(EnigmaPythonSources.Dialects
  ADD_TO_PARENT EnigmaPythonSources)

# This invokes TableGen to generate `_enigma_ops_gen.py`
declare_mlir_dialect_python_bindings(
  ADD_TO_PARENT EnigmaPythonSources.Dialects
  ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}/mlir_enigma"
  TD_FILE dialects/EnigmaOps.td
  SOURCES
    dialects/enigma.py
  DIALECT_NAME enigma
)

# Build EnigmaModule.cpp as a Python extension
declare_mlir_python_extension(EnigmaPythonSources.Extension
  MODULE_NAME _mlirDialectsEnigma
  ADD_TO_PARENT EnigmaPythonSources
  SOURCES
    EnigmaModule.cpp
  EMBED_CAPI_LINK_LIBS
    MLIREnigmaCAPI
)

# Pull in upstream MLIR's core Python sources + our dialect
set(_source_components
  MLIRPythonSources.Core
  MLIRPythonSources.Dialects.builtin
  MLIRPythonSources.Dialects.func
  MLIRPythonSources.Dialects.memref
  MLIRPythonSources.Dialects.arith
  MLIRPythonExtension.Core
  EnigmaPythonSources
)

add_mlir_python_common_capi_library(EnigmaPythonCAPI
  INSTALL_COMPONENT EnigmaPythonModules
  INSTALL_DESTINATION python_packages/mlir_enigma/_mlir_libs
  OUTPUT_DIRECTORY "${ENIGMA_PYTHON_ROOT_PREFIX}/_mlir_libs"
  RELATIVE_INSTALL_ROOT "../../../.."
  DECLARED_SOURCES ${_source_components}
)

add_mlir_python_modules(EnigmaPythonModules
  ROOT_PREFIX "${ENIGMA_PYTHON_ROOT_PREFIX}"
  INSTALL_PREFIX "python_packages/mlir_enigma"
  DECLARED_SOURCES ${_source_components}
  COMMON_CAPI_LINK_LIBS
    EnigmaPythonCAPI
)
```

> Note: the exact set of `MLIRPythonSources.Dialects.*` components to
> pull in depends on which upstream dialects you want available from
> Python. Start with `builtin`, `func`, `memref`, `arith` — these are
> the minimum needed to build a kernel that loads/stores memrefs and
> does float arithmetic. Add more (e.g. `scf`, `affine`, `vector`) as
> the DSL grows.

## Build Instructions

After all files are in place:

```bash
cd Enigma-Dialect
cmake -S . -B build -G Ninja \
  -DMLIR_DIR=/path/to/llvm-build/lib/cmake/mlir \
  -DLLVM_DIR=/path/to/llvm-build/lib/cmake/llvm \
  -DENIGMA_ENABLE_PYTHON_BINDINGS=ON \
  -DPython3_EXECUTABLE=$(which python3) \
  -DCMAKE_BUILD_TYPE=Release

ninja -C build
```

Build artifacts land in `build/python_packages/mlir_enigma/`. That
directory is a valid Python package — add it to `PYTHONPATH`:

```bash
export PYTHONPATH="$(pwd)/build/python_packages/mlir_enigma:$PYTHONPATH"
```

## Smoke Test

Before wiring up Enigma-DSL, verify the bindings in isolation. Save
as `test_bindings_smoke.py`:

```python
from mlir import ir
from mlir.dialects import func, memref, arith
from mlir.dialects import enigma

with ir.Context() as ctx, ir.Location.unknown():
    enigma.register_dialect(ctx)
    module = ir.Module.create()

    with ir.InsertionPoint(module.body):
        f32 = ir.F32Type.get()
        memref_ty = ir.MemRefType.get([1024], f32)
        fn_type = ir.FunctionType.get([memref_ty, memref_ty, memref_ty], [])
        kernel = func.FuncOp("vector_add", fn_type)

        with ir.InsertionPoint(kernel.add_entry_block()):
            A, B, C = kernel.arguments
            # Use an enigma dialect op — the exact op class name
            # matches what TableGen generated from EnigmaOps.td.
            tid = enigma.ThreadPositionInGridOp(
                dimension=ir.IntegerAttr.get(
                    ir.IntegerType.get_signless(32), 0))
            # ... (rest of body)
            func.ReturnOp([])

    module.operation.verify()
    print(module)
```

If this runs without error and prints a module containing an
`enigma.thread_position_in_grid` op, the bindings are working.

## Known Pitfalls

1. **Op class names.** TableGen derives Python class names from the
   op's `Enigma_Op<"kernel", ...>` record. `enigma.kernel` becomes
   `KernelOp`. Double-check actual generated names by inspecting
   `build/python_packages/mlir_enigma/dialects/_enigma_ops_gen.py`
   after the first successful build.

2. **Region-carrying ops.** `enigma.kernel` has a body region. The
   generated builder will take a `num_regions` or similar argument —
   check the generated code and pass the correct values. Region
   population is done via `ir.InsertionPoint` just like `func.FuncOp`.

3. **Attribute types.** If your op takes an `I32Attr`, the Python
   builder expects `ir.IntegerAttr.get(ir.IntegerType.get_signless(32), value)`.
   For `StringAttr`, `ir.StringAttr.get("value")`. TableGen-generated
   builders are strict about attribute types.

4. **Dialect C++ namespace.** The `MLIR_DEFINE_CAPI_DIALECT_REGISTRATION`
   macro in Layer 1 must reference the exact C++ class defined by
   your dialect. If it's `mlir::enigma::EnigmaDialect`, use that;
   if it's just `enigma::EnigmaDialect`, adjust accordingly.

5. **Library naming.** The CMake target `MLIREnigmaDialect` in the
   CAPI CMakeLists is a placeholder — substitute whatever your
   existing dialect library target is actually named.

## What Happens Next (in Enigma-DSL)

Once these bindings are built and working (checklist below passes), the
Enigma-DSL side will — WITHOUT writing any C++/pybind11/TableGen code —
do the following, all in pure Python:

1. Add `Enigma-Dialect` as a git submodule (already done) and wire
   `scikit-build-core` to build it as part of the DSL wheel build.
2. Replace `enigma/compiler/metal_emitter.py` (string emitter) with
   `enigma/compiler/mlir_emitter.py` that walks the existing
   `KernelBuilder` IR and constructs equivalent MLIR ops via
   `from mlir.dialects import enigma`.
3. Run MLIR passes (verification, canonicalization) on the module by
   calling into MLIR's Python `PassManager`.
4. Call into `enigma-translate`'s logic to lower the module to MSL.
   Ideally via a C API function exposed from this repo (a follow-up
   to this document), not via subprocess.
5. Feed MSL into the existing Metal runtime dispatch path (unchanged).
6. Package everything — DSL Python code + this repo's
   `python_packages/mlir_enigma/` + all bundled `.dylib` files — into
   a single wheel via `cibuildwheel` + `delocate-wheel`.
7. Publish that wheel to PyPI as `enigma-dsl`.

All of the above is scoped to the Enigma-DSL repo and uses these
bindings as an external library. No changes to this repo are needed
for that work — the bindings produced here are the stable contract.
